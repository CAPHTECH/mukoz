# 11 開発の進め方

作って試し、必要なら再設計する探索型の開発を、判定の信頼性を落とさずに速く回すための工程。設計(01〜10章)の実行順序はこの章に従う。

## 11.1 ゴール

### 構造

| 種類 | 内容 | 扱い |
|---|---|---|
| **目的** | AIエージェントが、ソースなしで、契約を満たすバイナリを生成・修正できるようになる | 開発の成否はこれで測る |
| **制約** | Mukozの判定が信頼できる。誤って合格させず、分からないことは保留にする | 品質契約(11.3)。目的のために緩めない |
| **設計上の制約** | 複数のホスト・検査対象に対応できる構造、自己検査 | 構造として守る。実際の対応環境の拡大は目的の検証を待たせない |
| **段階目標** | `linux-x86_64` の Tier 1(09章 9.8)、他ホスト、自己検査の段階1〜3 | 最初の探索目標(11.2)の後 |

### 用途

| 用途 | 扱い |
|---|---|
| (i) AIが機械語を直接生成する | **主用途**。ルーチン単位の検査・診断情報・回帰ケースを優先する |
| (ii) コンパイラが作った配布物をプラットフォームごとに検査する | 主用途にしない。ホストと同じOSの実行ファイルを native-process で起動し stdout・終了コードを調べる範囲は、(i) のために作る機能でそのまま使える。libcの動的リンクのエミュレーション、別ホスト向け配布物の実行、配布物向けの専用機能には投資しない |
| (iii) ソースのない第三者のバイナリ部品 | 範囲外 |

(ii) の扱いは、11.2 の比較試験の後に再判定する。

### 目的にしないこと

バイナリの正しさの証明、ソースレベルのテストの置き換え、マルウェアsandbox、対応環境の数そのもの。

## 11.2 最初の探索目標: 価値の仮説の比較試験

> **仮説:** AIエージェントは、Mukozを使うと、使わない場合より、正しいバイナリへ確実に・少ない反復で到達し、しかも誤った合格を出さない。

### 試験の設計

| 項目 | 内容 |
|---|---|
| 課題 | x86_64 SysV の小さなルーチン。レジスタだけの課題(add・sub・符号付き/符号なし比較・min/max)と、メモリを使う課題(コピー・文字列長・checked increment)。初期案は8課題前後 |
| 条件A(Mukozあり) | 契約・Binding・Suite を渡す。`mukoz check` → 診断 → 修正の繰り返し |
| 条件B(Mukozなし) | 同じ仕様を文章で渡す。ホストの `as` / `ld` と実行は自由。テストは自分で書く |
| エージェント | Claude の subagent。課題×条件ごとに3回(結果のばらつきを見るため) |
| 終了 | エージェントが「完成」と宣言したとき、または反復の上限に達したとき。上限は条件A・Bで同じにする |
| **最終判定** | **Mukozに判定させない。** 提出後に新しい seed で生成した追加ケースを、実CPU(native-routine 相当の独立したハーネス)で実行し、参照計算(手で確定した値の表、またはRust/Pythonで独立に書いた参照実装)と比べる。提出前には存在しないケースなので、エージェントは見られない |

### 測るもの

- 最終判定で正しかった提出の割合
- **誤った合格**: 条件Aで Mukoz が ACCEPT_WITHIN_SCOPE、最終判定で誤り。条件Bでエージェントが完成と宣言、最終判定で誤り
- 到達までの反復回数、経過時間、分かればトークン量
- 詰まった箇所(診断が足りない、契約が読めない、CLIの使い方等)

数値の合格線はここでは置かない。結果を見て関門Rで判断する。

### 限界

- 結果はこのモデル(Claude)と、この課題群に限る。
- 条件Bのやり方(エージェントが自分で書くテスト)は一つの比較対象にすぎない。
- 最終判定のハーネスも誤り得る。手で確定した値で最終判定のハーネス自体を先に確認する。

### 実施した設計からの逸脱

- **アセンブラ等は両条件とも禁止**(条件Bに `as` を許すと、条件差が「符号化の誤り」ではなく「道具の有無」で決まるため)。禁止は指示だけで、強制はしていない
- 課題×条件ごとに **1回**(3回ではない)
- 生成に加えて、**修正課題**(不具合を1つ入れたバイナリ `given.bin` を渡す。条件 RA / RB)と、**異ISA課題**(x86 ホストで aarch64 を生成。条件Bはネイティブ実行できない)を追加
- 最終判定: x86 は C の native runner(`eval/oracle/runner.c`)。aarch64 は Unicorn に依存しない独自の A64 整数部分集合インタプリタ(`eval/oracle/a64.py`、対応外の命令は FAIL)。どちらも提出後に新しい seed で 3,000 ケース。判定器は、参照実装が PASS し変異が FAIL することを課題ごとに確認済み(各1回)。a64.py は故障注入4種もすべて FAIL

### 結果(2026-10-04、各1回)

| 区分 | 課題 | 条件A / RA(Mukozあり) | 条件B / RB(Mukozなし) |
|---|---|---|---|
| 生成 x86 | abs_diff, fill, popcount, checked_mul, memmove, hex_encode, shl_var, isqrt | 8/8 PASS、`mukoz check` 各1回で ACCEPT | 8/8 PASS |
| 生成 aarch64 | memmove, hex_encode, base64 | 3/3 PASS、各1回で ACCEPT | 3/3 PASS(各自が A64 シミュレータを自作) |
| 修正 x86 | count_byte(64bit比較)、memmove(前方コピーのみ)、isqrt(最上位ビット欠落) | 3/3 PASS、各1回 | 3/3 PASS |
| 修正 aarch64 | base64(パディング判定の即値) | 1/1 PASS、1回 | 1/1 PASS |
| 生成 罠あり | count_byte_fast(8バイト単位の SWAR を要求。よく知られた零バイト判定は借りの伝播で誤検出する)x86・aarch64 | 2/2 PASS、各1回 | 2/2 PASS |
| 修正 コンパイラ出力 | base64(gcc -O2 -fPIC、384B・表込み、末尾2バイト経路のマスク 0x3c→0x38) | 1/1 PASS、1回 | 1/1 PASS |

- **誤った合格: 0件**(Mukoz ACCEPT かつ最終判定 FAIL は 0/18。条件Bの「完成」宣言かつ FAIL も 0/18)
- 最終提出 36件すべてに Mukoz を後からかけても ACCEPT で、最終判定と一致した
- 罠あり課題では4件とも誤検出しない厳密な判定式を最初から選んだ。罠の変異(誤検出する判定式)は Mukoz・最終判定とも検出した(各1回、x86・aarch64)
- コンパイラ出力の修正: 条件RAは Mukoz を確認に1回使っただけで、不具合の特定は手での逆アセンブルによる(本人の報告)。条件RBは自作テストで「2バイト端数の3文字目だけが誤る」と絞ってから該当箇所を読んだ
- **REJECT は一度も出なかった。**全エージェントが1回目で正解に到達したため、Mukoz の反例・診断が修正に役立つかは**この試験では観測していない**
- 異ISAでの差(観測、各1回): 条件Aは道具呼び出し3回・所要 25〜51秒。条件Bは 4〜6回・58〜83秒で、全員が検証用の A64 デコーダ/インタプリタを自作した。うち1件は自作シミュレータ自体に不具合があり1回やり直した。条件Bの報告は全員「自分の符号化と自分のデコーダが同じ誤読を共有していれば検出できない」と述べた
- 修正課題では、A・B とも全員がバイトを手で逆アセンブルして不具合を特定した(規模 21〜252 バイト)

### 契約作成の試験(2026-10-04、各1回)

エージェントに spec.md・docs(04/05/07)・正しい参照バイナリだけを渡し、契約・Binding・Suite を書かせた(memmove、hex_encode)。

- 作成された契約は、私の参照を ACCEPT・私の変異を REJECT(両課題、1回)。作成者自身の変異も hex_encode 14/14、memmove 17 のうち想定どおり REJECT(非停止1件は HOLD、符号付き比較の1件は検出できず)
- ツールの不具合として報告されたもの(すべて修正、受け入れテストと故障注入で確認): 事前条件がほぼ全ケースを捨てても ACCEPT / 生成器の不正な項目・値域が黙って無視 / `len` > max_len を黙って切り詰め / 境界値の直積を黙って縮小
- docs と実装の食い違い: docs/04 §4.10・docs/07 に 0.1 の実装範囲を固定した
- **未解決(設計の不足、`[U]` 未対応):**
  - 領域の部分範囲の権限がない(「src[0..n) と dst[0..n) だけに触れる」を正確に書けず、領域をぴったりに取る近似になる)
  - 領域の配置(番地・alignment)を生成できない。番地が 2^63 をまたがないため、方向判定の符号付き比較の誤りを検出できなかった
  - 式に let 束縛がなく、同じ部分式を繰り返す
  - ランダム生成の重み付けができない

### 解釈

- [R] **この課題規模(手書き〜70命令、コンパイラ出力〜400B)では、Mukoz の有無は正しさを変えなかった。**モデルが1回で正しく書け、修正も読んで特定できてしまうため。根拠: 36件すべて1回目で PASS。外れる条件: 別モデル・より大きな課題
- [R] **Mukoz の効いた所は「独立した検証が手に入ること」。**実行できない ISA では、条件Bの検証は自作シミュレータ(=自分の理解の写し)に頼るしかなく、手間も増えた。条件Aは独立した実行器と契約で確かめられた。根拠: 異ISA 4組の観測と報告。外れる条件: 条件B側に qemu 等がある環境
- ゴール(11.1)に対しては、**小さなルーチンの範囲で「Mukoz を使い、ソースなしで、契約を満たすバイナリを生成・修正できる」ことを 18件(各1回)で確認した。**「REJECT から反例を読んで直す」ループは未観測

## 11.3 品質契約

探索中でも緩めない条件。構文・ファイル形式・モジュール構成・CLI・内部の型は自由に再設計してよい。次の条件と「正解の独立性」を緩める変更だけは代表の判断を要する。

| ID | 条件 | 検証 |
|---|---|---|
| I1 | 検査できなかったこと(未対応・観測不能・予算切れ・欠測)を成功にしない | 負の試験 |
| I2 | subject context が変わった証跡を使い回さない | 負の試験 |
| I3 | Executor を自動で切り替えない | 負の試験 |
| I4 | REJECT は予告した性質IDと、再実行できる反例を伴う | 変異 fixture |
| I5 | 有効ケース0件は HOLD | 負の試験 |
| I6 | 期待値を Mukoz の実装から作らない | fixture はアセンブリから作り、期待はCPU・手で確定した表・独立実装から取る |
| I7 | 既定は emulated のみ。native 実行は関門を通ってから | 負の試験と代表のレビュー |

| 軸 | 条件 | 検証 |
|---|---|---|
| 再現性 | 同じPlanで同じ結果。fixture をソースから作り直せる | クリーン環境での再実行、digest一致 |
| 移植性 | Core はホスト非依存 | 他ターゲット向けの `cargo check`(ターゲットの追加が必要 `[U]`) |
| AIの使いやすさ | CLI出力だけで修正まで回せる | 11.2 の比較試験 |
| 性能 | 閾値は未定 | 最初のスライスで基準を測り、その後に合意する |

## 11.4 手法

| 手法 | 判定 | 要点 |
|---|---|---|
| 再現可能な環境を最初に通す | pilot | Unicorn が最大の不確実性。試作 1-A に通るまで、エンジンに依存する実装を進めない |
| 細い縦断スライス | adopt | 1本ずつ、負の試験込みで通す |
| 独立した受入例 | adopt | スライスごとに fixture と期待を実装より先に作る |
| 差分検証 | adopt | emulated と実CPU。どちらもQEMU由来の誤りを共有し得ることを明記 |
| 狙った変異 | adopt | 変異 fixture と、判定規則の手書き変異(例: HOLD→ACCEPT)。`cargo-mutants` は試してから判断 |
| 反例・回帰・修正の一組化 | adopt | Mukoz自身の不具合も、失敗する試験 → 修正 → 回帰試験の順 |
| 速い失敗と段階的な試験 | adopt | 試験を3段に分ける(Core → エンジン → 全fixture)。最後の関門では全段を実行 |
| 作り直せる fixture | adopt | アセンブリ → バイナリ → manifest。試験ごとに `.mukoz` を一時ディレクトリに作る |
| 正本の一本化 | adopt | 実装した部分はコード・schema・fixture が正本。docs は差分と状態だけ直す |
| 仕掛りの制限 | adopt | 縦断スライスは常に1本。並列は独立した作業だけ、subagent は最大2体 |
| 危険箇所のレビュー | adopt | native実行・試行区域・判定規則は代表がレビュー。別系統モデルのレビューは native を有効にする前に任意で1回 |
| 追跡 | adopt(最小) | 試験名に I1〜I7、ADR、受入基準のIDを入れる。新しい帳票は作らない |
| 全工程のコスト観測 | adopt(最小) | スライスごとに経過時間・再設計回数・手戻り・試験時間を1行で `docs/devlog.md` に書く |
| 試作と判断の分離 | adopt | 試作は `spikes/` に置き本体へ入れない。問いと合否を先に書き、結果を ADR に残す |
| 再設計の発火条件 | adopt | 11.6 |
| 検証結果のキャッシュ | defer | 今の詰まりを解かない |
| 形式モデル | reject | 範囲外(ADR-16) |
| 開発手順のスキル化 | defer | 最初の関門Rで手順が固まってから判断。正本は本章 |

## 11.5 工程

```text
G0 品質契約の確定
 ├─ 1-A 試作: Unicorn ────────┐
 ├─ 1-B 試作: 実CPU実行 ──────┤
 ├─ 1-C fixture整備 ──────────┤
 └─ 2 基盤とCore ─────────────┴─→ 3 スライス1(レジスタ) ─→ R
                                      │
                                      ▼
                          3b スライス2(メモリ領域) ─→ R
                                      │
                     E1 評価ハーネス ─┤ (3と並行可)
                                      ▼
                          4 比較試験(11.2) ─→ R(目的の判定)
                                      │
                                      ▼
                          5 拡張の反復(結果に応じて順序を決める) ─→ 各回 R
                                      │
                                      ▼
                          6 linux-x86_64 Tier 1 受入
```

| 工程 | 目的 | 依存 | 終了条件 | 止める条件 |
|---|---|---|---|---|
| G0 | 11.3 を試験名と期待のレベルまで確定 | — | I1〜I7 の負の試験の名前と期待が書かれている | — |
| 1-A | Unicorn の Rust binding のビルド、x86_64 add64 の1件実行、メモリ・コード・sentinel のフック、フック付きの速度の概算 | — | 4項目が動き、版を記録できた | ビルド不能・フック不足 → 代替(版の変更、システムビルド、命令を絞った自前インタープリタ)を ADR にして R |
| 1-B | Linux での mmap・トランポリン・シグナル捕捉・seccomp strict | — | x86_64 add64 が子プロセスで動き、syscall が止まる | seccomp が効かない → native-routine を試行区域から外す |
| 1-C | add64・sub変異・未対応命令の x86_64 fixture と manifest | — | 作り直して digest が一致 | — |
| 2 | workspace、ツールチェーン固定、3段の試験、式言語、TOML読込み、Assessor、Store | G0 | 負の試験・式評価の既知値試験が通る。Core が他ターゲット向けに `cargo check` を通る | — |
| 3 | 09章 9.5 の縦切り(`--artifact`、`--fail-fast`、回帰、診断、可能なら差分) | 1-A合格、1-C、2 | ACCEPT・REJECT・HOLD・回帰の検出が期待どおり | 品質契約を満たせない → R |
| 3b | 領域・ポインタ・状態(コピー、文字列長、checked increment) | 3 | guard とbyte単位の監視で範囲外アクセスを検出する変異が REJECT | 同上 |
| E1 | 比較試験のハーネス: 課題・契約・最終判定(独立した参照と実CPU)、条件Bの手順 | 1-B(実CPUで最終判定するため) | 最終判定ハーネスが手で確定した値で正しく判定する | — |
| 4 | 11.2 の比較試験 | 3b、E1 | 全課題×条件×3回の記録がそろう | 費用が見込みを大きく超える → 回数を減らす前に代表に確認 |
| R | 学んだことを設計へ戻す | 各スライス、4 | 仮説ごとに維持/変更を決め、ADR に記録 | 品質契約を緩める案 → 代表の判断待ち |
| 5 | 結果に応じて: 診断・契約の書き方の改善、AArch64 ルーチン、静的ELFプロセス、Mach-O、自己検査 | 4 の R | 各スライスで受入例・負の試験・変異検出が通る | — |
| 6 | 09章 9.8 の10項目 | 5 | 全項目に証跡がある | 未確認が残れば Tier 1 にしない |

工程4の結果が「Mukozありの方が良くない」または「誤った合格が出る」なら、工程5に進む前に、診断情報・契約の書き方・CLI を再設計して工程4をやり直すか、目的そのものを見直す。

## 11.6 再設計

**発火条件**(どれかが起きたら関門Rに入る):

1. 試作の合否関門に落ちた
2. 不変条件を設計どおりに実装できない
3. 比較試験・AIループで、診断情報やCLIが原因で詰まった
4. 2スライス続けて使われない設計要素がある(削る候補)

それ以外の気付きは `docs/devlog.md` に記録し、次のRでまとめて判断する。

**手順:**

1. 短い ADR を 10章に追加する(問題、観測、選択肢、決定)。
2. 影響する docs の節だけを直し、README の章の状態(設計のみ / 試作で確認 / 実装済み)を更新する。
3. コードと試験を変える。
4. I1〜I7 の試験が通ったままであることを確かめる。

## 11.7 役割

| 役割 | 担当 |
|---|---|
| 代表 | 品質契約の変更、native実行・隔離のレビュー、ライセンス、パッケージ導入の判断 |
| Claude(主) | 統合、設計の保守、レビュー、比較試験の運営 |
| ワーカー | Claude の subagent。互いに独立な作業(試作 1-A / 1-B 等)は `isolation: worktree` で並列にし、統合は主が行う。最大2体 |

subagent は主と同じモデル系列なので、レビューの独立性はない。独立性が要る判断(判定規則、native実行)は代表のレビューと、実CPU・手で確定した値などの独立した期待値で補う。

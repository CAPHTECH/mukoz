# F11は正常応答のまま解放後使用を起こし、Memcheckで検出された

隔離VMを使わず、F11の公開8ケースをV/R/Hの3成果物、native・GDB・Nulgrind・Memcheckの4条件で3回ずつ実行した。計288実行で照合エラーは0件。違反版の対象3ケースだけが毎回検出され、修正版と許可される対照版への誤検出はなかった。

今回検証したのは、既存のHTTPサービスと同じ初期化・ハンドラを `F11_STDIO` で呼び、応答を標準出力へ返す経路である。ソケットは開かない。Memcheckの記録は既存の正規化器とadapterに通し、`mukoz.external_claims/0` の `VIOLATED` まで確認した。既存のnative-processが単独で検出した結果ではない。

## ローカルでの結果

記録は `../evidence/f11-local-2.tar.gz` に保存した。`python3 ../restore_evidence.py` で `runs/f11-local-2/` に復元できる。集計は `summary.json`、環境・ビルド命令・成果物と評価コードのsha256は `env.json` にある。同じ3バイナリを全条件・全反復で使った。

| 条件 | 実行数 | 契約どおりの応答 | メモリ違反の結果 |
|---|---:|---:|---|
| native | 72 | 72 | メモリcapabilityなしとして72件NOT_EVALUATED |
| GDB | 72 | 応答は個別集計の対象外 | 解放後アクセス9件、ほか63件は命中なし |
| Nulgrind（C0） | 72 | 72 | 72件NOT_EVALUATED |
| Memcheck（C） | 72 | 72 | 9件VIOLATED、63件SATISFIED_IN_SCOPE |

対象はV/p05・p06・p08の3ケースで、3反復ともGDBとMemcheckが一致した。この9件はnative・C0・Cのすべてで契約どおりの200応答を返した。Memcheckは「65 byteの解放済み領域内の64 byte目で1 byteを不正読取り」と報告し、解放時と確保時のstackも残した。全プロセスは終了コード0で終了した。

各runには標準出力・標準エラー・終了コード・実行命令を保存した。CにはXML、正規化イベント、Mukoz形式の判定も保存した。SUTの応答とMemcheckの診断は別ファイルである。帰属は、各ケースを新規のprocess sessionで逐次実行したことに基づく `exclusive_process_group` とした。独立レビューを受けていないため、claimsのindependenceは `self` のままである。

`test_f11_local.py` の9試験では、確保元と解放元の識別、診断の削除・途中切れ、応答の改変、capabilityの欠如などを確認した。既存のMemcheck正規化器の14試験と故障注入9通りも通った。解放後使用のXMLでは2番目のstackが解放元なので、これを確保元としていた正規化器を修正し、`free_frame` と3番目のstackの `alloc_frame` を分けた。

初回の `runs/f11-local-1/` は探索記録である。GDBの同じwatchpointが再表示された回数を設定数として数えてしまい、27件の照合エラーを出した。識別番号の集合で数えるように直し、コードのhashを記録してから `f11-local-2` を実行し直した。初回を成功結果として数えていない。

## 再現する違反

`src/f11.c` は、本文と改行の要否をキャッシュするHTTPサービスである。`eol=1` の要求では本文を応答に複写し、改行フラグを参照して必要なら改行を足す。

| 成果物 | フラグの読取りと解放の順序 |
|---|---|
| V（違反版） | フラグを持つ領域をfreeし、その領域のフラグを読む |
| R（修正版） | フラグを読んでから領域をfreeする |
| H（許可される対照） | 別に確保した古い領域をfreeし、保持中の有効な領域のフラグを読む |

フラグは領域の先頭から64 byte後に置き、allocatorが先頭に書く管理情報との衝突を避ける。関数呼出しとvolatile読取りを使って、最適化したバイナリにもアクセスを残す。ただし、解放後の値や正常応答は保証されない。各条件の応答を実際に照合する。

`contract/F11.json` に公開8ケースとV/R/Hの事前ラベルを置いた。Vのp05・p06・p08だけが `MEM.HEAP.ADDRESSABLE` に違反する想定である。p07は存在しない項目への要求で、違反処理に到達しない。各ケースは新しいプロセスで、1要求を実行する。これは1実装・公開ケース・1反復の校正であり、保留ケースによる主比較ではない。

## 正解と判定を照合する

`gdb/F11.gdb` は、起動時に4項目のフラグへhardware watchpointを設定する。解放済みの項目へのアクセスだけを `WITNESS_HIT` として記録する。解放済みフラグの意味はソースと逆アセンブルのfree→フラグ設定→読取りの順序に依存する。SUTが出すPASS文字列やMemcheckの診断だけを正解には使わない。

`f11_check.py` は次を要求し、欠測や不一致をエラーにする。

- native（GDB監視）、a（観測器なし）、B、C0、Cの各24 runがそろい、3成果物のsha256が条件間で一致する。
- 違反版の禁止経路も含め、全120 runのHTTP応答が契約に合う。停止はcontrollerによるSIGTERMで、子孫の回収も完了する。
- nativeのGDB記録が事前ラベルに一致する。
- A0・A1・B・C0はメモリpropertyを未評価に保つ。Cだけが事前ラベルに従って違反／範囲内で充足と判定する。
- CのXMLに、`cached_flag` での解放済み領域のInvalidReadと、読取り・解放・確保のstackが残る。診断がSUTのstdout・stderrへ混ざらない。

## VMを使わない再実行

GCC・objdump・Valgrind・GDBが使える環境で、既存出力と重ならない名前を指定する。

```sh
cd research/security-observation/fx
python3 f11_local.py runs/f11-local-next
python3 test_f11_local.py
```

`f11_local.py` は3反復を既定とし、`--valgrind`・`--gdb`・`--debug` でツールや追加デバッグ情報の場所を指定できる。GDBには、自分が起動する子プロセスをptraceで監視できる権限が必要である。負の試験は保存済みの `f11-local-2` の記録を使う。

今回、ツールはDebianパッケージを `/tmp/mukoz-f11-tools` に展開して使った。システムへのインストールはしていない。Valgrind 3.24.0、GDB 16.3、GCC 14.2.0。展開したツールでの実行命令は次のとおり。

```sh
VALGRIND_LIB=/tmp/mukoz-f11-tools/root/usr/libexec/valgrind \
LD_LIBRARY_PATH=/tmp/mukoz-f11-tools/root/usr/lib/x86_64-linux-gnu \
PYTHONHOME=/tmp/mukoz-f11-tools/root/usr \
python3 f11_local.py runs/f11-local-next \
  --valgrind /tmp/mukoz-f11-tools/root/usr/bin/valgrind \
  --gdb /tmp/mukoz-f11-tools/root/usr/bin/gdb \
  --debug /tmp/mukoz-f11-tools/debug
```

展開したlibc6-dbgのbuild IDを実際のloader・libcと照合し、Valgrindの追加検索先にdebuglink名のシンボリックリンクを置いた。システムへ通常インストールしたValgrindと対応するデバッグ情報を使う場合、この設定は不要である。

## 残る比較範囲

ローカルでの解放後使用の再現、正常応答、独立したGDB監視、MemcheckからMukoz形式への違反判定は確認できた。HTTPの通信経路、OS観測器B、既存Pilotと同一条件でのF10/F11比較、保留入力、別の作者の実装は今回の対象に含めていない。18.2のCの採用判断は引き続き保留とする。

VM用の `f11_run.sh`・`f11_check.py` も残してあるが、ローカル検証には使わない。VMで開始した最初のnative実行は、接続断後に記録一式を回収できていないため、上記の結果には含めない。

E1の計画器は契約の `implementations` を参照する。F11は `[1]` とし、未実装の2系統目を計画へ入れない。
